### Candidate35 AboutActivity focus-loss ANR — repaired in candidate36

At 2026-10-29 13:20:03 +0800, candidate35 process PID 12567, Task 3676, logical Display 13, reported `Input dispatching timed out ... FocusEvent(hasFocus=false)` for `com.kaori.wakeupschedule/.intro.AboutActivity`. The page had rendered (`.tmp/phase16-diagnostics/candidate35-about-display13.png`), but the subsequent focus-loss/Back route stalled and the schedule capture was black (`candidate35-after-about-back-display13.png`).

The DropBox trace shows a lock cycle. The main thread is in `com.bumptech.glide.load.engine.OooO0o.OooO00o`, waiting for a Glide engine lock owned by `glide-disk-cache-thread-7`, while holding `o00000O0.o000oOoO`. That disk-cache thread owns the engine lock and waits for `o00000O0.o000oOoO`, held by the main thread. The trace places the main thread in `Glide` `LifecycleLifecycle.onStart` during `AboutActivity` startup. Comparing recovered Java with the original Smali identified the lock-order mismatch: the Java methods called `Engine.OooO0Oo(...)` from inside `synchronized(this)`, while Smali releases the job monitor before the engine callback. Candidate36 moves the engine/callback work outside the monitor and retains pending-work accounting. Full trace: `.tmp/phase16-diagnostics/candidate35-latest-anr-20261029-1320.txt` (SHA-256 `277ED4E91BCD2A90174FF240A1E8C387700AA1D3527BAC478764F3AA66927E3C`).

Candidate36 validation launched AboutActivity on logical Display 16, PID 14004, Task 3679. It remained responsive for about 30 seconds; Back returned to ScheduleActivity, whose window remained drawn and focused. No new app ANR, input-dispatch timeout, or fatal-signal line appeared during roughly 55 seconds after opening About. Evidence: `.tmp/phase16-diagnostics/candidate36-about.png`, `candidate36-after-about-back.png`, `candidate36-final-home.png`, `candidate36-final-activity.txt`, `candidate36-final-window.txt`, and `candidate36-final-logcat.txt`.
